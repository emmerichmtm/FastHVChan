\section{Experiments and their interpretation}
\label{sec:experiments}

These measurements concern the previously published \emph{global-interval
adaptive} implementation, archived with revision \texttt{38587e7}~\cite{software}.
They do \emph{not} measure the new local-checkpoint driver
\texttt{numerical\_chan\_local\_compiled.py}, which uses a different schedule.
Source hashes identify the files actually timed.

\subsection{Inputs, implementations, and measurement protocol}

The main suite contains 45 standard inputs: for each dimension from 2 to 10,
two spherical fronts, two tied grids, and one magnitude instance on the smaller
spherical front. Three additional inputs force compression in dimensions 4,
7, and 10, giving 48 inputs altogether. Spherical corners are positive,
normalized vectors formed from absolute Gaussian samples with a positive
offset, and hence mutually nondominated.
The grids can contain ties, duplicates, and dominated corners. Point counts
decrease with dimension; this is a collection of small practical examples,
not an experiment estimating an asymptotic exponent.

Four implementations are compared: compiled numerical, original numerical
Python, and the repository's Python Chan $d/3$ and $d/2$ implementations.
Chan $d/3$ is omitted in 2D. The compiled solver uses sweeps in 2D/3D and
native contractions with Python geometric recursion in 4D--10D. Numerical
Python retains its earlier local block schedule, so this compares complete
implementations rather than compilation alone. Compression remains enabled.
No dominance filtering, fast-math, or parallel execution is used. Solvers
receive equivalent unions; magnitude uses the affine HV transformation for
the Chan references.

Sequential fresh workers perform one separately recorded first call and
three timed calls, each with a fresh solver. Warm medians include conversion
and preprocessing but exclude imports; verification warmed the compilation
caches. The 45-second worker budget includes startup, imports, and every
call. A timeout is not a per-call lower bound.
The recorded processor identifier is AMD64 Family 25 Model 80 Stepping 0,
with 16 logical CPUs. The environment used Windows 11, Python 3.12.14,
NumPy 2.5.3, and Numba 0.68.0; CPU affinity was not fixed. All raw samples,
inputs, counters, signatures, and source hashes are archived~\cite{software}.

Of 187 algorithm--input workers, 186 completed and one timed out: numerical
Python on the six-point 9D sphere. All 48 compiled workers completed.
Across ordinary-hypervolume inputs in dimensions 4--10, compiled numerical
was faster than Chan $d/3$ on 26 of 28 pairs, with median ratio of reference
time to compiled time $2.02$. Against numerical Python, it won 26 of 27
completed pairs, with median ratio $6.29$. Chan $d/2$ was faster on all 28
ordinary-hypervolume pairs in these dimensions. These completed-pair ratios
exclude magnitude, forced compression, and timeouts. They provide no general
claim that the compiled solver is the fastest hypervolume implementation.

Variability is material. Across the 48 compiled workers, the ratio of slowest
to fastest warm repetition had median $1.28$ and maximum $2.74$; five workers
exceeded a ratio of two. There were no deliberately concurrent solver or
oracle jobs, but ordinary system load was uncontrolled. Three samples do not
provide reliable confidence intervals, and small differences should not be
overinterpreted.

\subsection{What the compression experiments establish}

All 35 standard inputs in dimensions 4--10 executed \emph{zero} compressions
in the compiled solver. Their adaptive size gates were checked 994 times,
but the states stayed below the threshold. Thus the main timing table
measures the benefit of pruning and native evaluation on these inputs; it
does not measure the cost of required compression. The three forced cases
use the first eight corners of a 4D spherical input, padded with unit extents
for 7D and 10D. With interval two and threshold factor zero, each executes
one compression and reaches a peak of 135 terms. All values agree with the
reference. These checks exercise the implementation, but are excluded from
the performance aggregates.

A separate structural input exercises the global-interval implementation's
\emph{unchanged defaults}. For each of the six coordinate pairs in 4D, it
contains 256 corners with pair extents $(t,257-t)$, $1\leq t\leq256$, and
extent 300 in the other coordinates. Add 16 corners
$(161+i,176-i,161+j,176-j)$ with $0\leq i<16$ and
$j=3i\bmod16$. This gives 1,552 boxes. The first 1,536 become pair
constraints, leaving long arrays with few remaining hard boxes. Shared
extents are intentional; this is not a general-position performance sample.

The compiled run performs six compressions and returns
$6\,372\,330\,876$, exactly the floating-point value returned by both Chan
references. Table~\ref{tab:natural-compression} records all six events.
Every event starts above the size threshold, yet every resulting state is
larger by the stored-entry count. In particular, the first compression
changes one term into 296 terms. Compression preserves the required cell
masses and coarsens the coordinate domains; it need not immediately reduce
the complete representation.

This probe visited 47 nodes, emitted 6,358 raw terms, and performed 1,352
variable eliminations. Its single first-use computations took 2.432 seconds
for compiled numerical, 1.235 seconds for Chan $d/3$, and 0.459 seconds for
Chan $d/2$, using existing caches. They are \emph{not warm medians} and are
excluded from Table~\ref{tab:adaptive-sphere-times} and all timing ratios.
Chan $d/3$ performed no compression: its breakpoint representation and the
numerical array representation have different size measures. This experiment
establishes that default compression is operational, not that it improves
runtime or storage. Repeated compression along one path is checked in the
separate correctness suite, not established by this probe.

\subsection{Correctness evidence and its limits}

Every available first-call and warm value was compared with Chan $d/2$.
An independent oracle also evaluated exact rational inclusion--exclusion on
the binary64 input coordinates for the 34 saved inputs with at most 12
points, including all three forced cases. All 543 recorded values passed;
the largest scaled error was $6.3811\times10^{-16}$, where scaling divides
absolute error by $\max(1,|\text{reference}|)$. The comparison tolerances were
$2\times10^{-9}$ relative and $2\times10^{-10}$ absolute. Oracle input hashes
match the archived dataset and timing files.

The proofs concern exact arithmetic; the compiled implementation uses binary64
and signed intermediate sums, without a general floating-point error bound.
Local algebraic closure also does not establish the old adaptive driver's
global runtime. The new local-checkpoint analysis is separate from this
benchmark; practical performance of that policy remains to be measured.
